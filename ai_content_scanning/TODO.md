# AI Content Scanning Service — TODO

## Назначение сервиса

Сервис отвечает за автоматическую проверку пользовательских вложений (фотографий) перед их публикацией в системе. Основная цель - фильтрация неприемлемого контента и проверка релевантности загружаемых изображений тематике городских проблем.

Согласно архитектуре системы (C4, Container Diagram), сервис взаимодействует с Background Worker: тот передаёт вложения на проверку, а AI Content Scanning Service возвращает результат.

---

## Варианты реализации API

### Вариант 1 — Синхронный REST API 

Наиболее простой способ интеграции. Background Worker отправляет HTTP-запрос напрямую на эндпоинт сервиса и ожидает ответа.

POST /check_image
Content-Type: multipart/form-data

Тело запроса: { "file": "<бинарный файл изображения>", "issue_id": 123 }

Ответ: { "status": "ok", "issue_id": 123, "confidence": 0.97, "reason": null }

Поле status принимает значения ok или rejected. При отклонении поле reason содержит причину (например, irrelevant_content или inappropriate_content). Поле confidence отражает уверенность модели в результате (от 0 до 1).

Плюсы: простота реализации, удобство отладки.
Минусы: блокирует Worker на время обработки, плохо масштабируется при высокой нагрузке.

---

### Вариант 2 — Асинхронная обработка через очередь сообщений 

Background Worker публикует задачу в очередь scan_queue брокера сообщений (RabbitMQ). AI-сервис читает задачи из очереди, выполняет проверку и публикует результат в очередь scan_results_queue. Backend подписан на результаты и обновляет статус заявки в базе данных.

Структура сообщения в очереди: { "issue_id": 123, "file_url": "s3://bucket-name/uploads/photo_123.jpg", "timestamp": "2025-04-13T21:00:00Z" }

Сервис не принимает файл напрямую — он скачивает его из Object Storage по ссылке, что исключает двойную передачу бинарных данных.

Плюсы: не блокирует основной поток обработки, легко масштабировать горизонтально, устойчив к пиковым нагрузкам.
Минусы: сложнее в реализации и отладке, требует настройки RabbitMQ.

---

## Передача данных: сравнение подходов

multipart/form-data (файл напрямую) — малые файлы, простая интеграция, MVP.
Ссылка на файл в S3 — продакшн, крупные файлы, асинхронная обработка.
Очередь сообщений (RabbitMQ) — высокая нагрузка, масштабирование.

Рекомендуемый подход: Worker кладёт файл в Object Storage и передаёт в сервис только ссылку (file_url). Это снижает сетевую нагрузку и упрощает повторную обработку при ошибках.

---

## Что должна проверять модель

- Релевантность — изображение соответствует тематике городской проблемы, а не является, например, селфи или случайным фото
- Модерация контента — отсутствие насилия, шокирующих или запрещённых материалов
- Дубликаты — изображение не является дублем уже поданной заявки (через сравнение хешей или векторных эмбеддингов)

## Варианты моделей 

OpenAI GPT-4o Vision — коммерческая, высокое качество, простая интеграция через API, платно.
Google Cloud Vision API — коммерческая, хорошо подходит для модерации, платно.
CLIP (OpenAI, open-source) — подходит для проверки релевантности, бесплатно, требует развёртывания.
LLaVA — open-source, мультимодальная модель, бесплатно, высокие требования к железу.
